# VibeCast — архитектурные решения и компромиссы

Формат: решение → причина → последствия/ограничения. Все отклонения от ТЗ
зафиксированы здесь.

## D1. Протокол: HTTP + Range, без real-time стриминга

**Решение.** ПК скачивает файл целиком по HTTP (параллельно с воспроизведением
URL в mpv) и кэширует на диск. Звук декодируется и выводится локально mpv.

**Причина.** Требование ТЗ; устойчивость к пропаже сети, нулевая задержка повтора.
**Последствия.** Первый play зависит от скорости LAN; при обрыве сети во время
первого проигрывания возможна остановка, если трек ещё не докачан. Кэш-файлы
занимают место на диске; управление кэшем — в настройках.

## D2. Android: Ktor CIO + общий JVM-модуль `android/shared`

**Решение.** HTTP-слой вынесен в чистый Kotlin/JVM-модуль (`shared`), Android
поставляет реализации `VibeCastDataSource` (MediaStore/ContentResolver). Сервер
запускается Ktor CIO на `0.0.0.0`.

**Причина.** Позволяет тестировать авторизацию, пагинацию и Range-ответы
интеграционными тестами Ktor без эмулятора; один и тот же код работает на
устройстве.
**Последствия.** `shared` зависит от Ktor server-core; Android-модуль добавляет
только engine и UI.

## D3. Bearer-токен: 32 случайных байта, EncryptedSharedPreferences

**Решение.** Токен генерируется `SecureRandom` (32 байта, Base64 URL-safe без
padding), хранится в `EncryptedSharedPreferences` (AES256-GCM). Сравнение —
constant-time. Токен не пишется в логи, не публикуется в mDNS TXT.
**Fallback.** Если Keystore/EncryptedSharedPreferences недоступен (редкие
прошивки), используется приватный `SharedPreferences`; факт фиксируется в логе
без значения токена. Это осознанный компромисс ради работоспособности MVP.
**QR.** URL вида `http://<ip>:<port>/#token=<token>`; токен в fragment, чтобы не
попадать в серверные логи при открытии в браузере.

## D4. Идентификатор трека

**Решение.** `id = SHA-1("<MediaStoreId>:<size>:<dateModified>")` (40 hex).
**Причина.** Стабилен между перезапусками, меняется при замене файла/метаданных,
не раскрывает пути. Используется в URL и как имя кэш-файла.

## D5. Версия каталога и SSE

**Решение.** Версия хранится в prefs, увеличивается на 1 при изменении множества
id (добавление/удаление/замена файла). SSE отдаёт текущую версию сразу после
подключения и затем при каждом изменении; heartbeat — комментарий `: ping` раз в
15 с.
**Ресинк на ПК.** При получении новой версии клиент перезагружает каталог
страницами по 500 и атомарно заменяет таблицу `tracks` в SQLite. Инкрементальный
diff-протокол не вводится: для 20k треков полный ресинк занимает сотни мс и
исключает рассинхронизацию. Это трактовка «инкрементального обновления» —
обновление инициируется версией, а не polling'ом.

## D6. Desktop: Tauri 2 + React + SQLite + reqwest

**Решение.** Tauri 2 (Rust core), React 18 + TypeScript + Vite, виртуализация
`@tanstack/react-virtual`, состояние `zustand`, SQLite через `rusqlite` (bundled),
HTTP/SSE через `reqwest` (rustls), mDNS через `mdns-sd`.
**Причина.** Tauri даёт нативный процесс mpv и доступ к файловой системе/сети без
CORS-ограничений; SSE нельзя подписать Authorization-заголовком из браузерного
`EventSource`, поэтому поток читает Rust.
**Последствия.** Все сетевые вызовы и обложки идут через Tauri-команды (обложки
возвращаются data URL). UI не делает прямых запросов к телефону.

## D7. mpv как дочерний процесс, IPC per-platform

**Решение.** mpv запускается лениво при первом play с флагами
`--idle=yes --no-video --gapless-audio=yes --audio-buffer=0.3` и
`--input-ipc-server` (Windows named pipe `\\.\pipe\vibecast-mpv-<pid>-<nanos>`, Unix
socket в cache-каталоге). Авторизация передаётся **не аргументом процесса**, а
опцией `loadfile` (`http-header-fields`), чтобы токен не был виден в списке
процессов.
**Поиск бинарника.** Настройка `mpv_path` → `VIBECAST_MPV` → `<resource_dir>` →
`PATH` → типовые пути, включая `C:\Program Files\MPV Player\mpv.exe`. Бинарник mpv
не входит в репозиторий и не бандлится: пользователь ставит его сам (README).
**Завершение трека.** `--keep-open=no` не всегда присылает `eof-reached`, поэтому
IPC `end-file` обрабатывается отдельно: `eof` → событие `player://eof` (UI берёт
следующий трек), `error` → понятное сообщение без падения приложения.
**Ограничение.** Gapless между разными треками не гарантирован: каждый трек
загружается отдельным `loadfile`, флаг `--gapless-audio=yes` сглаживает границы
внутри файла. Полноценный gapless-плейлист mpv — кандидат на следующую итерацию.

## D8. Кэш аудио

**Решение.** Windows: `%LOCALAPPDATA%\vibecast\audio`, Linux/macOS:
`~/.cache/vibecast/audio`, файлы `{trackId}.{ext}`; недокачанные — `.part` с
докачкой через `Range`. Кэш наполняется фоновой задачей одновременно с
воспроизведением URL. Индикатор «Стрим/Кэш» в плеере.
**Последствия.** Если телефон исчез, уже закэшированные треки играют; трек,
который не успел скачаться, может остановиться. После завершения загрузки
текущего трека клиент не переключает источник на лету (следующий play — с диска).

## D9. Хранение токена на ПК

**Решение.** Токен и URL активного сервера хранятся в SQLite в каталоге данных
приложения; файл БД создаётся с ограниченными правами (по возможности). В логи
токен не попадает, в UI маскируется.
**Причина.** MVP без OS-keychain; кроссплатформенный keyring тянет системные
зависимости.
**Ограничение.** Токен на диске не зашифрован; отмечено как риск.

## D10. Без TLS

**Решение.** HTTP в LAN, как разрешено ТЗ. Токен защищает от случайного доступа,
но не от прослушивания трафика.
**Ограничение.** Не использовать в недоверенных сетях; TLS и подтверждение
устройства — следующая итерация.

## D11. Поиск и сортировка на ПК

**Решение.** Поиск выполняется SQL-запросом в SQLite по колонке `search_text`
(Unicode-lowercase, собранной в Rust — корректно для кириллицы, в отличие от
SQLite `lower()`). UI получает отфильтрованный список (до 20 000) и виртуализирует
его. Сортировки: title/artist/album/duration.
**Причина.** «Серверный» поиск относительно UI, мгновенная реакция, нет N+1.
**Последствия.** Передача ~4 МБ JSON на полный список 20k; дебаунс 180 мс.

## D12. Очередь — в UI, mpv — один трек за раз

**Решение.** Очередь хранится в zustand (массив треков), eof приходит из Rust
событием `player://eof`, UI запускает следующий. Next/prev — команды UI.
**Причина.** Простота и предсказуемость; mpv-плейлист потребовал бы двусторонней
синхронизации позиций.
**Последствия.** См. D7 про gapless; при закрытии окна очередь не сохраняется.

## D13. mDNS

**Решение.** Android публикует `_vibecast._tcp` с TXT `version`, `token_required=1`,
`device`. Desktop непрерывно броузит через `mdns-sd` 0.21 и показывает найденные
устройства; подключение требует токен (QR/ручной ввод). При недоступности mDNS
работает ручной URL. Токен по mDNS не передаётся.
**Выбор адреса.** Телефон может рекламировать несколько IPv4 (Wi-Fi + VPN).
Клиент предпочитает адрес из той же /24, что и локальный маршрут ПК, затем
192.168/10/172.16; публичные, CGNAT и link-local адреса отбрасываются. Без этого
Windows выбирал адрес Radmin VPN и подключение шло не туда.

## D14. Оффлайн и переподключение

**Решение.** Каталог при старте читается из SQLite; статус «оффлайн», если
`/health`/SSE недоступны. SSE-цикл в Rust переподключается с backoff 3 с, при
успехе делает ресинк. Кнопка/автоповтор не требуется.
**Последствия.** Пока телефон выключен, играются только кэшированные треки;
UI явно сообщает об этом.

## D15. Dev-мок UI

**Решение.** Демо-источник в `src/lib/mock.ts` включается только при явном
`VITE_MOCK=1` и только вне Tauri. Без этого флага браузерная страница показывает
понятную ошибку, а не фальшивую библиотеку. В Tauri-приложении мок не используется
никогда.
**Причина.** В окружении нет Android-устройства, поэтому мок нужен для визуальной
проверки UI. Но пользователь не должен видеть «стандартные» треки до подключения
телефона.

## D16. Целевые версии

Android: minSdk 26, target/compileSdk 35, Kotlin 2.0.21, AGP 8.7.3, JDK 17
toolchain. Desktop: Rust edition 2021, Tauri 2, React 18, TypeScript 5.6,
`mdns-sd` 0.21.6, mpv 0.41 (проверочная версия). Версии зафиксированы в lock-файлах
(`package-lock.json`, `Cargo.lock`).

## D17. Windows DPI и размер окна

**Проблема.** Tauri-окно логически 1280×820 при масштабе 125% занимало 1600×990
physical на экране 1536×864: правый край и player bar уходили за пределы экрана.
`GetWindowRect` показывал виртуализированные координаты и вводил в заблуждение.

**Решение.** Добавлен `app.manifest` с Common Controls, `dpiAware=true/pm`,
PerMonitorV2 и supportedOS; `build.rs` подключает его через
`WindowsAttributes::app_manifest`. Стартовый размер уменьшен до 1200×620
(min 960×560), центрирование. Проверено: внутренний viewport 1200×620, весь UI
виден при 125%.

## D18. Dev-мок и mock-сервер

**Dev-мок UI** (D15) — отдельная реализация Tauri-команд в `src/lib/mock.ts`,
активна только вне Tauri и только с `VITE_MOCK=1`. Она не попадает в IPC
продакшена и нужна для визуальной проверки в браузере.

**Mock-сервер** `scripts/mock-server.mjs` — независимая реализация Android-
протокола без зависимостей: 8 треков, WAV, Range/416/HEAD, обложки PNG, SSE,
Bearer-токен. Нужен для интеграционной проверки Rust-сети, кэша, mpv и mDNS без
телефона. Это тестовый инструмент, не часть приложения.

## D19. Контракт обложек

`coverId` в `/library` — **число** (`Long?`), а не строка: так его отдаёт Android
(MediaStore album id). Mock-сервер сначала отдавал строку, из-за чего Serde не
парсил каталог; контракт зафиксирован числом и проверен интеграционно. Обложки на
ПК кэшируются как `{trackId}.img`, в UI передаются data URL.

## D20. Офлайн-политика play

Перед play проверяется `online` и наличие файла в кэше. Если трек не кэширован и
телефон офлайн, команда сразу возвращает понятную ошибку, а не пытается открыть
недоступный URL и зависнуть. Кэшированный трек играет всегда. Статус `online`
обновляется SSE-циклом и успешным ресинком.

## D21. Чистый старт и явное отключение

**Решение.** Новый ПК начинает с пустым каталогом: никаких встроенных или
демонстрационных треков. Треки появляются после успешного подключения телефона и
сохраняются в SQLite для офлайн-прослушивания кэша. Явное действие «Отключить»
удаляет сессию, каталог и останавливает mpv; кэш-файлы остаются, но недоступны без
повторного подключения.
**Причина.** Требование «треки только после подключения телефона»; при этом
аварийное исчезновение телефона не должно ломать офлайн-режим (D14).

## Известные ограничения MVP

- Нет TLS (D10) и шифрования токена на ПК (D9).
- Нет камеры/сканирования QR на ПК — токен вводится вручную или вставляется с URL.
- Нет gapless между треками (D7), нет repeat/shuffle-режимов сервера.
- Метаданные не редактируются, плейлисты — только папки артистов/альбомов.
- Тесты на реальном Android-устройстве/эмуляторе и 30-минутный тест экрана в этом
  окружении не выполнялись; см. docs/TESTING.md.
- Проверено только на Windows 11; Linux/macOS-ветки не запускались.
- Тайминги первого play и нагрузка на 20k треков не измерялись инструментально.
