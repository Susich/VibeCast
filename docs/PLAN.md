# VibeCast — план разработки MVP

Дата старта: 2026-10-29. Ответственный: senior full-stack / tech lead.

## Продукт в одном абзаце

Android-телефон раздаёт локальную музыкальную библиотеку по HTTP (каталог, аудио с
Range, обложки, SSE). Windows/Linux/macOS-клиент на Tauri находит телефон по mDNS
или подключается вручную, хранит каталог в SQLite, показывает библиотеку и играет
файлы локально через mpv. Звук — всегда на ПК. Никакого real-time стриминга.

## Архитектурные границы

- Протокол: HTTP/1.1, Bearer-токен на всех ручках кроме `/health`.
- `GET /health` — публичный, без секретов.
- `GET /library?offset=&limit=&q=` — пагинация + серверный поиск по подстроке,
  поле `version` монотонно растёт при изменении состава каталога.
- `GET /audio/{id}` — файл, `Accept-Ranges: bytes`, один Range → 206.
- `GET /cover/{id}` — JPEG/PNG обложки.
- `GET /events` — SSE, событие `version` при изменении каталога + heartbeat.
- ПК тянет файл по URL при первом play и параллельно кэширует на диск; повторный
  play идёт с диска. mpv — дочерний процесс (sidecar), управление по JSON IPC.

## Фактический результат

- **Android:** 23 JUnit-теста (`:shared:test`) покрывают маппинг каталога, Range
  (200/206/416/HEAD), Bearer-авторизацию, пагинацию, поиск, обложки и SSE. APK
  собран (`app-debug.apk`). Реального устройства/эмулятора в окружении нет —
  сценарии permission/FGS/30 минут экрана отмечены как непроверенные.
- **Desktop:** строгая TypeScript-сборка и `cargo test` (6 тестов: URL/токен/SSE,
  выбор LAN-адреса mDNS) проходят. Интеграционно проверены реальные Tauri WebView,
  mpv 0.41, mock-сервер: подключение, проигрывание, пауза/seek/громкость,
  next/eof, кэш и повтор с диска, SSE-обновление версии, офлайн-режим и
  переподключение, mDNS-обнаружение (`desktop/src-tauri/examples/publish_mdns.rs`).
- **DoD:** всё, что можно проверить без Android-устройства, проверено; честный
  список «не проверено и почему» — в TESTING.md.
- **После первого запуска на телефоне:** исправлен краш mDNS
  (`getServiceName(...) must not be null`), mDNS сделан необязательным для работы
  сервера; ПК начинает с пустым каталогом, демо-треки отключены, явное отключение
  очищает каталог. Подробности — TESTING.md §9.


## Стратегия проверки в этом окружении

В системе Windows 11, JDK 21, Node 24, Rust 1.99 + MSVC, WebView2, Android SDK 35,
mpv 0.41. Нет Android-устройства и эмулятора.

- Общая JVM-логика (модели, маппинг, Range-парсер, HTTP-модуль Ktor) вынесена в
  `android/shared` и покрыта JUnit-тестами через Ktor `testApplication` — это
  позволяет проверить 206/401/пагинацию/SSE без телефона.
- Android APK собирается CLI-сборкой; установка на устройство и проверка экрана —
  вне возможностей окружения, фиксируется в TESTING.md.
- Desktop: Rust-модули тестируются `cargo test` (URL/SSE/mDNS). Реальная
  интеграция проверена на Tauri WebView + mock-сервере + установленном mpv.
  Дополнительно UI проверяется в in-app браузере на Vite dev-сервере с dev-моком.
- Range/авторизация проверены curl'ом против mock-сервера и JUnit-тестами против
  Ktor-сервера; на реальном телефоне — не проверялись.

## Критерии приёмки (из ТЗ)

См. корневой README и docs/TESTING.md. Каждый пункт DoD получает строку
«проверено / не проверено / почему» с командой или тестом.

## Риски

1. JDK 26 несовместим с AGP → используем toolchain 17 и отдельный JDK 21 для
   Gradle.
2. `EncryptedSharedPreferences` на некоторых прошивках падает → fallback с
   приватным prefs + запись в DECISIONS.
3. Android FGS restrictions (API 34+) → тип `dataSync`, запуск из Activity,
   постоянное уведомление, Wakelock/WifiLock.
4. mDNS в Windows бывает заблокирован файрволом → ручное подключение обязательно.
5. Без TLS токен виден в LAN → известное ограничение MVP.
